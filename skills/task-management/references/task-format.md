# Task format

- Create one task per clear action or outcome.
- Start the title with a verb.
- Make the title specific enough to understand the work from list view. Keep it concise, with a soft cap around 12 words, but clarity beats being too short.
- Avoid client or project names in the title unless needed for clarity.
- Do not use colons in titles.
- Include month and year for time-bound campaigns when needed.
- Begin task bodies with one or more short paragraphs that explain the whole problem, why it matters, what created the need, and what good resolution means.
- Task bodies must carry enough context for a capable human or agent to execute at high quality without rediscovering the basics.
- Write bullets as natural-language prose that adds context, constraints, evidence, or known unknowns. Do not use key-value labels like `Source:`, `Repo:`, `Context:`, `Acceptance criteria:`, or checklist-style instructions.
- Task bodies should describe the problem and execution context, not prescribe a rigid step-by-step procedure. Include only guidance that prevents wrong work, duplicated discovery, or risky assumptions.
- For website, app, theme, or code work, include the repository URL or local repo path when known. If no repo is found after checking likely sources, say that explicitly in the task body and ask for the repo before execution.
- For design or content work, include the design file, brief, brand assets, copy source, attachments, examples, or source thread when available. If required assets are missing, say exactly what is missing.
- Before writing bullets, search likely source systems and repos for the real docs, links, files, screenshots, scripts, commits, and constraints.
- Do not pretend context exists. If an important source cannot be found, either ask for it or record the missing source clearly in the task body.
- Use acceptance criteria only when they help clarify done. Do not replace source context with generic acceptance criteria.
- Keep due dates and other property data out of the description.
