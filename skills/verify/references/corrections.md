# Correct the right layer

Use for an explicitly rejected result, unexpected evidence contradicting an accepted requirement, outcome, or result already presented to the user, or a recurring failure worth learning from. Expected red tests and disproven implementation hypotheses remain ordinary iteration in the implementation procedure. Pause the affected action and compare the accepted outcome with the actual result. Recheck the evidence; neither the previous verdict nor the latest comment alone proves the cause.

A question or tentative reaction is not necessarily a rejection. Clarify before changing direction when intent is unclear. If feedback conflicts with an accepted constraint or another stakeholder's direction, surface that conflict rather than letting the latest comment silently win.

## Route the correction

- If the artifact violates the accepted requirement, repair the artifact and relevant regression coverage within the existing scope.
- If the requirement or preference changed, update the accepted task or specification. Ask one focused question when the new direction or tradeoff is unclear; do not silently broaden the work.
- If project facts, configuration, fixtures, or verification steps are wrong, correct their project-owned source. Keep project-specific facts out of organization-wide guidance.
- If a recurring mechanical error can be prevented by a test, type, lint, or script, prefer that check over another instruction. Verify it catches the failure without blocking valid behavior.
- If the procedure itself causes a generalizable error, propose the smallest change to its existing canonical owner. If the procedure was adequate but not selected or followed, fix discovery, the worker brief or capability choice, or execution instead of adding duplicate policy.
- If the host or external service is responsible, use its supported recovery or escalation path. Do not build a parallel lifecycle to mask a platform problem.

Choose the narrowest layer that explains the evidence. Repetition is a signal to investigate, not automatic permission for a shared rule or automation.

## Preserve authority

An in-scope repair needs no new planning ceremony. A new outcome, unclear preference, broader impact, or inferred shared policy needs the relevant decision or authorization before applying it. Technical capability and reversibility do not expand permissions.

Identify what changed since prior approval. Rerun affected checks on the corrected artifact; an old pass does not cover a new revision. Any change to approved communication text, recipients, destination, or attachments requires renewed send approval. A content change to the approved diff requires renewed merge approval before merging; a clean rebase or base update alone does not, unless it changes the content or invalidates an approval condition. Separate operational gates still apply. Never treat silence, a worker's success report, or correcting a draft as approval to publish it.

## Close the correction

Demonstrate that the original failure is resolved and the accepted constraints still hold. Reconcile records and stale readiness through the task-record and delivery procedures without duplicating tasks or time. Triage later feedback on completed work as a defect or new request. Follow the project's reopening policy; if none resolves whether to reopen or create a linked follow-up, ask before changing that status or creating new work. Draft any needed correction to another person for approval before sending.

Record only useful decisions and proven lessons in the appropriate source. Keep task-specific feedback out of global skills or memory; reusable personal preferences follow the host's memory rules, which do not replace canonical procedure updates. If blocked, state the unresolved outcome and smallest required decision. A corrected local result, a deployed fix, and a communicated correction are different states.
