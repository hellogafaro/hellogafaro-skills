# Options and prototypes

Name the question the options will answer. Reuse the project's visual language and constraints. Build two or three meaningfully different alternatives only when the choice is unresolved; an established pattern or a precise bug fix does not need a design competition.

Hold the content and comparison conditions constant where possible. Label each option, expose the interaction that differs, and give a recommendation with the tradeoff that could change it. Color variations of one idea do not count as different interaction or architecture options.

Choose the cheapest faithful form: side-by-side sketches for layout, a switcher for UI variants, or a small state demo for behavior. Use the shared kit for the presentation shell, not as a replacement for the project's own product design. Mark prototypes as throwaway and keep their data isolated from production.

Inspect every variant and the states that determine the decision. Present the options visually rather than burying them in descriptions. A chosen mockup is a design decision, not a completed feature or a passing runtime test.

Fold the accepted direction into the authorized implementation or canonical plan. Preserve the decision and useful evidence without promoting disposable code into production or creating a new durable artifact when the user asked only to explore.
